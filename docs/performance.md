# Performance contract

The production home screen uses one `/api/workspace` request. The Worker returns at most 40 summaries per page, authoritative totals, tag/collection counts, date aggregates and activity summaries. It performs search and filtering beside the indexed data. The browser only maps stable identifiers to display names and renders the result; it never downloads the entire archive to calculate the home screen.

- Pagination is bounded and counts remain global. Only changed search text is debounced by 180 ms; range/tag/collection navigation is immediate. Query keys normalize tag order, duplicates, defaults and equivalent match modes, and include the calendar day and cursor. Replaced requests are aborted and cannot overwrite a newer result.
- Before the first response, a layout skeleton indicates loading instead of reporting zero saved items. Subsequent refreshes retain the current page until a replacement is ready; failures never switch to demo content.
- `LiveStore` remains the sole editable data owner. Query responses are reused for 60 seconds, with LRU limits of 8 pages / 2 MiB of serialized payload. Switching to a cached filter or previous page does not refetch. TTL is measured from the response, never extended by a cache hit. An uncached filter never displays a different filter’s results. Explicit refresh bypasses freshness; the currently mounted list and reader survive same-query refresh, preserving scroll and playback. A successful empty response replaces previous content.
- Detail responses use a separate bounded cache (8 entries / 8 MiB, five-minute retention). Direct reuse lasts 60 seconds and requires both body and personal revisions to match the current summary. After that the server rechecks access and revisions; unchanged bodies reuse retained text, while images/media metadata come from the new response. Remote changes may take up to the freshness window to appear on navigation; manual refresh reads immediately. 401/403 workspace errors clear all visible data and caches, and 401/403/404 detail errors evict that article and hide its reader. Transient refresh failures retain the current body with an explicit retry notice.
- Deep links fetch the summary and selected article concurrently. Hover/focus lasting 150 ms preloads the reader chunk and one article detail; leaving early cancels the intent timer. Save-Data / 2G connections skip speculative loading. Selecting an in-flight prefetched article shares its promise. Prefetch does not mount the reader or fetch images/video.
- Every edit invalidates query/detail caches and aborts in-flight reads before creating the draft. Reads cannot replace unsaved work; save completion fetches authoritative summaries and selected detail. Nothing except language preference persists in browser storage; there is no service worker or replay of old demo/session data.
- Unsaved drafts, active writes and post-save reconciliation have distinct localized states. Closing an editor submits immediately after its final state is known; it no longer adds the toggle debounce. Only editing controls are disabled during submission; global navigation and scroll remain usable. Settings views do not refresh a hidden reader. Collection state tabs use one exclusive state for both styling and accessibility.
- Collection members load and paginate only when expanded. Save completion reloads the current summary page; it does not refetch all historical tag states. Global tag removal is performed by the backend rather than by scanning the current page.
- Fonts are the original design files, self-hosted with licenses. Static assets are precompressed at build time, fingerprinted, cached immutably and support conditional requests. Private API data remains no-store; the proxy forwards upstream compression and timing, and cancels work when clients disconnect.
- Date formatters are reused. Reader scroll progress updates a DOM ref instead of rerendering the whole article on every scroll event.

Before this change, three fresh-browser production measurements took 25.7–28.3 seconds to show data, made 98 API requests and transferred about 2.24 MB. Script execution took 0.16–0.17 seconds, identifying request fan-out and excess source transfer as the dominant bottleneck. Deployment measurements and runtime versions are recorded in the operations history; this baseline is not a promise of identical latency on every network.

Regression checks include a 10,000-item metadata fixture that still makes one home request, stale-search cancellation, full-library counts with paged results, lazy reading with body revisions, legacy CRUD, desktop/mobile behavior and the pinned design screenshot comparison. Production acceptance is GET-only and must not invoke paid models or write synthetic bookmarks.

## Frontend navigation optimization (2026-10-13)

The previous UI used one `loading` flag for initial load and every refresh, emptied list results while fetching, and replaced the reader with a status message. It had no workspace query reuse and fetched each reopened detail. A GET-only browser run measured home readiness at 1.99 s (workspace response 1.45 s), repeated range switches at 1.41–1.43 s, and reopening at 0.87 s. These are one-run network observations, not backend execution measurements. The eight-action scenario made eight API calls; cold loads still depend on network/server response latency. No backend, database, Worker or API proxy changes are part of this optimization.

The approach follows [Karakeep’s stable browser query client and 60-second freshness](https://github.com/karakeep-app/karakeep/blob/main/packages/shared-react/providers/trpc-provider.tsx) and [SWR’s distinction between initial loading and background validation](https://swr.vercel.app/docs/advanced/understanding). The existing store is retained to avoid competing caches for mutable drafts; no source from either project is copied.

Regression coverage checks TTL and memory limits, query/cursor identity, cancellation, in-flight deduplication, revision matching, draft/cache invalidation, denied access, parallel deep-link loading, preserved reader DOM and scroll during refresh, and fresh-browser isolation.

## Static delivery and failed navigation (2026-10-13)

An authenticated cold deep link on OCI took 31.48 s to mount the video reader: 41 font requests transferred 1.39 MB, ahead of high-priority API requests. The session fetch took 6.39 s while its response-header wait was 130 ms. Blocking fonts reduced reader readiness to 18.50 s; the entry script still spent 8.06 s downloading from the origin. These are browser/network observations, not PostgreSQL execution times.

Production can set `CAIRN_ASSET_BASE=https://cairn-static.alpenl.com/` at build time. Vite rewrites JS, CSS, dynamic imports and fonts to that public asset origin. The default remains `/` for local/demo/NAS builds. Private API and archived media URLs remain rooted at `/api` on the authenticated application origin; no credentials or article contents enter the CDN. Keep original font files and Unicode subsets to preserve the design. The CDN serves only GET/HEAD `/assets/*`, with immutable caching and public CORS; other routes return 404. Retain old fingerprinted files so already-open clients and rollback builds can still load their lazy chunks.

The HTML and API do not use the asset CDN. Match the app CSP to the configured asset origin for script/style/font loading, validate cross-origin module and font CORS, and deploy assets before atomically switching HTML. CDN failure is observable as a resource error, never substituted with demonstration data. Operational rollout and rollback are recorded in the deployment runbook.

A failed uncached filter used to keep `queryPending` true because the last successful result belonged to a different filter. Loading now ends in an explicit retryable error; prior-filter items stay hidden and retry keeps the requested filter. Same-query refresh continues to retain valid content. API/session fetches explicitly request high priority. Regression coverage includes a failed filter followed by successful retry.

When selected detail data confirms a playable archived attachment, preload the shared player module immediately alongside the reader chunk. The UI still mounts/loads media only through the existing viewport rules; preloading JavaScript never downloads private image/video bytes or starts playback. This removes the reader-chunk → render → player-chunk waterfall without adding player code to the home bundle.
